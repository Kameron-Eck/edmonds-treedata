## Job 2 — the account-wide quota counter

**Page.** `GET /account/` (logged in) prints `Fast downloads used (last 18 hours): N / M`. The page's own HTML comment
says any "24" in the numbers is rendered `<span>2</span>4`.

**Parser: `annas.parse_quota`.**
- It drops comments, scripts and styles, then removes tags **without** inserting a space, unescapes entities and
  collapses whitespace.
- The regex must match, and every match must agree.
- No match, disagreeing matches, or a limit of 0 returns `None` (fail closed).
- **Reader: `annas.read_quota`.** One GET; a non-200 answer or an exception gives `None`.

**Gate.**
- `annas.fetch_for_litkb(..., quota_margin=)` reads the counter after gates 1–2 and the known-md5 short-circuit, so a
  `duplicate-held` costs no account request. It reads it again before the download request.
- When `used >= limit - margin`, or when the counter is unreadable, it returns `quota-stop` and **never asks
  `fast_download.json` for a URL**.
- After a URL is issued it re-reads the counter. The result carries `quota = {used_before, used_after, limit, margin,
  account_status}`.
- `run.acquire` always passes `budget.quota_margin`. It stores `quota` in the `acquisition_attempts` detail, sets
  `budget.stopped` on a `quota-stop` (so the rest of the run makes no more archive requests), and the CLI prints
  `account_counter`.

**Local guards kept.** The run cap on issued URLs (`max_archive_downloads`) and the old `downloads_left <= margin` stop
remain as second guards.

**Margin.** The default is **50** (`--quota-margin`), documented in `run.Budget`. It is 5 % of the 1000 limit, kept as
head-room for:
- downloads that the browser or another session spend in the same 18-hour window, between the read and the request;
- the counter lagging a spend.

**Cost.** Two unpaced GETs of a ~170 KB page per download attempt. That is fine at this volume; say so if it grows.

**Tests** (no network; stubbed HTML):
- `test_account_counter_parser_reads_only_the_counter`, 8 cases, each as str and bytes:
  - the saved page → `(4, 1000)`;
  - the `<span>2</span>4` form → `(24, 1000)`;
  - entities and newlines → `(7, 1000)`;
  - `account_counter_missing.html`, where the counter exists only in a comment and a script → `None`;
  - `account_counter_wording.html` ("last 24 hours", "left today") → `None`;
  - two disagreeing counters → `None`;
  - `0 / 0` → `None`;
  - an empty page → `None`.
- `test_read_quota_fails_closed_on_a_bad_answer`.
- `test_archive_reads_the_account_counter_before_every_download_request[at_margin, past_limit, unreadable, below_margin]`:
  - In the three stop cases: 0 `fast_download` calls, a `quota-stop` attempt, and a second work in the same run makes
    no archive request at all.
  - Below the margin: the download runs, and the stored detail's `quota` is `used_before 949`, `used_after 950`.
- The fixtures `qc/testdata/litkb_p2/account_counter*.html` are an excerpt of the real page. The account id is replaced
  and the invite link removed; the page shows only a link to the secret key, never the key itself.

**G1 (proposal, not fixed): a second DOI of an admitted work, admitted alone, makes a second work.**
- **Why it happens.** Check 2 looks identifiers up exactly, and title review runs only when there is no strong identifier.
  The live run avoided it by admitting Page once with both DOIs, which the design supports; a bulk load from rows that
  each carry one DOI would not avoid it.
- **Evidence on `litkb_test`.** A strict xfail, `test_a_second_doi_of_an_admitted_work_does_not_make_a_second_work`. It
  was not reproduced on `litkb`: a registry admission is a fact in main and there is no delete path.
- **Proposal.** For a registry admission whose DOI is new, run the title-duplicate review against works of the same year
  ±1 and the same first author, and send hits to duplicate review instead of admitting.

### Proposals (not built)

- **P-1: admit the work, hold the file.** `admit --file` refuses the whole admission when the file does not bind, even
  though check 1 passed (5 works here). P3's bulk load by DOI + file would drop every IMS/JSTOR cover scan and every
  OCR-damaged byline this way. Admit on the registry record, and record the file's hold as an attempt. This run did that
  by hand, so it left 5 refused admission rows.
- **P-2: known cover sheets.** On IMS–JSTOR "collaborating with JSTOR" covers (Hudson, Hwang, Anderson), page 1 has
  under 200 characters and the paper starts on page 2. Read page 2 when page 1 is a recognised cover, and fix the stored
  reason: it says OCR is needed when it is not.
- **P-3: route to OCR.** Title ratio ≥ 0.85 with the author missing from the text layer (Kingman, Maragos) is exactly what
  re-OCR could fix, but `binding-failed` is terminal and only `binding-pending` waits for OCR (§15.14). Give that pattern
  its own pending state.
- **P-4: dead archive status.** `bad-file` is not in `DEAD_STATUSES["annas"]`, so each later acquire re-requests. It is
  quota-free on the same md5, as measured, but it is wasted traffic on the known slash-suffix partner-404 class.
- **P-5: quarantined md5s.** The disk index's md5s include `_quarantine\`, so a quarantined wrong-content file can make
  the archive route answer `duplicate-held`. Here the same bytes are also the bound Validation copy, so no harm was
  measured. Excluding `_quarantine` from `known_md5` would close it.
- **P-6: key slugs.** French stopwords (`le`, `des`, `de`) and registry section prefixes ("Part 4: …") end up in keys.
