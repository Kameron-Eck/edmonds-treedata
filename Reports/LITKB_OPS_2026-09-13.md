## 1. Nightly dump — `Scripts/pipeline/litkb/ops/nightly_dump.py`

**What it does.** It runs `pg_dump -Fc -w` of `litkb` as `litkb_owner`, with the password read from the pgpass
file and never passed on the command line. It writes `<name>.partial` in `D:\edmonds-pipeline\pgdump\litkb\`,
verifies that file, then renames it to `litkb_<UTC>.dump`. It records the sha256 in `manifest.json`, prunes to the
newest 14 dumps and appends one line to `nightly_dump.log`. A dump that fails verification is renamed `*.rejected`
and never enters the manifest.

**Why verification has three stages (probed on a real 252 KB `litkb_test` dump).**

| Damage | `pg_restore --list` | `pg_restore -f -` (full read) |
|---|---|---|
| last 200 bytes cut | **passed** (rc 0) | failed: "end of file" |
| cut by 1, 50, 1,000 or 20,000 bytes | not run | failed, every one |
| cut to half | failed | failed |
| 28 garbage bytes at 1/3 of the file | crashed (segfault, rc 139) | crashed |
| 28 garbage bytes at 2/3 | **passed** | **passed** |
| 28 garbage bytes 5,000 bytes before the end | passed | failed: zlib "incorrect data check" |

- `--list` reads only the table of contents at the head of the file, so it is the cheap first stage only.
- The full read catches truncation.
- Neither stage catches every kind of corruption. So the sha256, taken after both stages pass, goes into the
  manifest. Retention and `--verify-existing` re-hash against it. This catches damage at rest. It cannot catch a
  file that `pg_dump` wrote wrongly in the first place: that case rests on the full read, and on the weekly
  restore check.

**Restore check.** It runs weekly (whenever the last good check is 7 or more days old), or on `--restore-check`.
- The superuser creates `litkb_restore_check` in litkb's tablespace and revokes PUBLIC's CONNECT on it. The owner
  cannot do this: it has NOCREATEDB.
- The dump is restored with `--exit-on-error`, and exact `count(*)` is compared for every table in `litkb` and
  `litkb_meta`. The scratch database is always dropped.
- Source counts are taken inside the same snapshot `pg_dump` used (`pg_export_snapshot` + `--snapshot`), so a write
  during the dump cannot produce a false mismatch.
- A mismatch exits 1, is logged as `restore=MISMATCH`, and is not recorded as a good check. Retention never deletes
  that dump.

**Retention.** It deletes only files that meet all three conditions:
- the manifest lists them;
- the name matches `^<db>_\d{8}T\d{6}Z\.dump$`;
- the bytes still hash to the manifest's sha256.

Anything else is left, and a note is logged.

## 2. Staged-secrets check — `Scripts/qc/secrets_check.py`, ladder rung `secrets`

**What it reads.** It reads git's **index** (`ls-files -s` plus one `cat-file --batch`), which is exactly what the
next commit contains. So one pass covers tracked and staged files. It is stdlib only and never prints a matched
value. It is rung 0 of `qc/check.py`.

**What it refuses.**
- **Names:** `*.pgpass`, `pgpass.conf`, `.env`, `*.env`, `.litkb-workstream`, or any path under `secrets/`.
- **pgpass lines:** a whole line shaped `host:port:db:user:password`, with a numeric (or `*`) port and a password of
  16 or more non-space characters.
- **Tokens:** a 64-hex value assigned with `=` or `:` to a name containing token, secret, api_key, password, pwd,
  bearer or auth.
- **Allowlist:** an inline `secrets-check: allow <reason>` (token rule only), or `ALLOW_PATHS` with a reason.
  **Both are empty.**

**False positives found.** The first run on the repository gave **82 findings, all false**, in
`phase4/qc/runtime_sessions.csv`. CSV rows of UTC timestamps (`x,,,,,2026-09-09T12:06:08Z,...`) parsed as
`host:port:db:user:password`. The fix: host, db and user may not contain commas. After it: **clean, 1,139 indexed
files, 4.6 s.** The leading name prefix in the token regex backtracked over every word (the rung took 23.2 s); the
regex now starts at the keyword.

**Kills** (throwaway git repositories under `tmp_path`). Ten planted cases are refused:
- a pgpass line in an innocently named `.txt` file;
- a pgpass line in a committed (tracked) `.md` file;
- a `.env` file;
- a `*.env` file;
- `pgpass.conf`;
- a `*.pgpass` file;
- `.litkb-workstream`;
- a file under `secrets/`;
- a yaml `api_token: "<hex>"`;
- a Python `WS_TOKEN = '<hex>'`.

Controls that pass:
- a sha256 digest column;
- timestamp CSV rows;
- a pgpass password shorter than 16 characters;
- code that formats a pgpass line;
- a token line carrying a pragma with a reason.

A pragma without a reason is refused, and unstaging the file clears the refusal. The repository test runs the check
on the real index and passes.

**Pre-commit hook: not installed.** `.git/hooks` is shared by every worktree of this repository, so installing it
would change other sessions' commits. To install it, run the one-liner in the script's docstring. Deleting the file
reverses it.

## 3. Race-test reliability — `Scripts/qc/instruments/litkb_race_flake.py`

**What a race test is.** One connection's transaction is held open, for example mid-`promote_commit`. A second call
starts on another connection in a thread. The test polls `pg_blocking_pids` until that call is seen waiting on the
first, or seen finishing without waiting. Only then does the holder commit, and the test checks the loser's outcome.
The ordering is forced by the lock itself, not by sleeps. If the guard's lock is removed, the second call does not
wait: it reads the pre-commit state and succeeds, and the test fails on the outcome.

**Method.**
- Each of the 11 race nodes in `test_litkb_p1.py` ran **30 times** in one pytest session per state, through the P1
  suite's own fixtures.
- **Unmutated, every run must pass. With its guard mutated, every run must fail.**
- Mutations are the harness rows, plus the acceptance verifier's N1, re-created in this instrument as two exact string replacements (it is not a harness row). The verifier's
  N2a is byte-identical to harness row F3b, so it ran once, as F3b.
- Files were sha256-restored after each mutation, and `git status` was clean of them afterwards.
- Raw rows: `Reports/litkb_race_flake_2026-09-13.csv`.

| Test (node) | Unmutated pass | Mutation | Mutated fail |
|---|---|---|---|
| D1 `test_write_blocked_behind_promote_commit_is_refused` | 30/30 | D1 (no FOR SHARE in `_write_version`) | 30/30 |
| D8 `test_losing_concurrent_writer_gets_40001[fact]` | 30/30 | D8 (no identity-row FOR UPDATE) | 30/30 |
| D8 `…[proposal]` | 30/30 | D8 | 30/30 |
| X9 `test_commit_waits_for_a_write_in_flight_and_is_refused` | 30/30 | X9 | 30/30 |
| X2 `test_concurrent_rebases_of_one_workstream_make_one_copy` | 30/30 | X2 | 30/30 |
| X3 `test_rebase_during_a_commit_that_moves_main_is_refused` | 30/30 | X3 | 30/30 |
| X1 `test_add_evidence_waits_for_a_prepare_in_flight_and_is_refused` | 30/30 | X1 | 30/30 |
| F2b `test_abandon_waits_for_a_prepare_in_flight_and_is_refused` | 30/30 | F2b (lock removed) | 30/30 |
| | | **N1** (check-then-lock) | 30/30 |
| F3b `test_add_use_embedding_waits_for_a_commit_in_flight_and_is_refused` | 30/30 | F3b = **N2a** | 30/30 |
| F7b `test_open_workstream_race_in_one_directory_leaves_no_orphan` (10 rounds each) | 30/30 | F7b (no O_EXCL) | 30/30 |
| F8 `test_token_is_bound_never_visible_in_pg_stat_activity` | 30/30 | none: no harness row | — |

**Verdict.**
- **330/330 unmutated runs passed. 330/330 mutated runs failed** (11 mutation-and-test pairs × 30).
- No race test was nondeterministic in this measurement, so none was changed.
- The acceptance report's open question ("how often these race tests would flake") is answered for 30 runs per
  state.

**Limits, stated.**
- **Same process.** The 30 repetitions shared one process, and the laptop was otherwise lightly loaded. Scheduling
  noise across processes and under heavy load was not sampled.
- **F7b is a real thread race.** The two openers meet at a `threading.Barrier`, so which one wins varies. The test
  accepts either order, and O_EXCL makes the outcome deterministic whichever wins.
- **D1 and D8 wait without a thread handle.** A mutated run that never blocks waits the full 15 s before failing.
  That affects speed, not the verdict.
